* Unified build contract

=./zbuild.py <command> [deliverable ...] [--profile release|debug]= defaults to release
and =deps grpc hpx folly nng= in that order. Select names explicitly for a narrower
delivery. =list= shows supported actions; =metadata= describes native engineering units
and outputs; =--dry-run= previews without requiring tools, signing material or services.
Old flag-only, stack-first and alias syntax is invalid.

=build= builds and materializes dependency packages in project-local
=build/staging/<profile>/<target>/=. It records success only after staging completes
and never publishes into =ZETA_INSTALL_PREFIX=. Folly's required gRPC packages are
staged before configuring Folly. =install= requires explicit target names and a
successful build of the same profile; it publishes only those targets without
rebuilding or rerunning Conan. Build prerequisites not explicitly selected for
installation remain staged only. CMake and pkg-config metadata are adjusted to
the publication prefix. =install deps= publishes the OpenSSL manifest with its
CMake package files. Rebuild =deps= if its stage lacks the manifest.
Forge validates the staged inventory and its external references before
publishing. Rebuild a target once if it only has a legacy completion stamp.
Publication reads the stage even if the original build directory has been
removed. It records owners and recovers interrupted writes under
=<prefix>/share/zeta_forge/native/=. Use a fresh prefix for the first install
if legacy files conflict. Folly requires a matching published gRPC stage.
HPX publication removes build-tree settings for HPX and its bundled Stdexec
from the installed CMake configuration.
=clean/rebuild= affect the named native
build directories and target staging for one profile, not installations or shared
Conan/Cargo caches. =rebuild= then rebuilds selected outputs and required dependencies.

The native =-j= budget applies to both CMake and Conan package builds.
The native dependency policy lives in =common/zeta_forge/conan_policy.py=.
Forge generates the recipe and its policy snapshot together for deps, HPX and
Folly. Use =zbuild.py= to prepare them.
These targets retain their Conan locks and resolution receipts under
=build/conan-state/<target>/<profile>/=. =rebuild= keeps the lock and regenerates
missing or changed outputs against it. Use =--refresh-conan-lock= with
=build=, =check= or =rebuild= to resolve a fresh lock for selected Conan targets.
=--dry-run= shows the requested refresh without resolving dependencies.

For Boost 1.91.0, =deps=, =hpx= and =folly= use a Forge recipe derived from a
pinned Conan Center revision. Forge exports the patched recipe into the local
Conan cache before resolution. Boost.Cobalt TLS uses the Conan OpenSSL selected
by =ZETA_OPENSSL_VERSION= (default =3.6.2=). The generated
=Boost::cobalt_io_ssl= target carries its Cobalt I/O and OpenSSL dependencies.
Other =ZETA_BOOST_VERSION= selections use the corresponding upstream recipe.

For Folly, Forge passes the Conan Libevent library and headers directly to
Folly's find module, avoiding the legacy CMP0026 branch on CMake 4. The same
configuration is used after a clean rebuild.

Forge =check= configures and compiles selected native libraries.
Explicit =doctor rust-deps= performs static offline dependency governance;
=check rust-deps= additionally resolves all registered Rust consumers with
=--locked --offline= and does not compile. =check rust-updates= explicitly queries
crates.io/GitHub for read-only upgrade candidates after loading locked offline
graphs; it does not adopt updates. =metadata/list/help/dry-run= for this target
only describe scope and never connect upstream. See
[[file:doc/en/rust_workspace.org][Rust governance]] for report schemas and failure semantics. =test= defaults to
=build-tools= and runs Python tooling tests, not upstream third-party test suites.
The default tests cover Forge's public entrypoint and shared adapters with
Forge-owned fixtures and require no sibling checkout or network access.
Run =python3 tests/manual/cmake_consumers.py= explicitly to check the real
sibling CMake entrypoints. It reports each available revision and returns a
failure if prerequisites or compatibility checks fail.
Unsupported upstream tests, runtime and fetch capabilities are errors. Host preparation
remains =common/prepare_debian.sh=; it is not a build action. No global Conan profile
is overwritten by build. Provision the selected Conan profile separately.

#+begin_src sh
./zbuild.py list
./zbuild.py build nng --profile debug
./zbuild.py rebuild nng --dry-run
./zbuild.py build deps nng
./zbuild.py install deps nng
./zbuild.py test
#+end_src

Public contracts: =common/zeta_forge/build_cli.py=; native adapters:
=cmake_engine.py=, =rust_engine.py=, =gradle_engine.py=; project definitions:
=builder/project.py= and =builder/<target>/project.py=. Applications keep their own
thin entry and project definition. There is no subsystem registry or alternate
native dependency graph. The root =zbuild.py= is the only executable Forge build entry.

* Phase 3 compatibility baseline

- The supported Python surface includes =build_cli.{Product,Project,Request,Engine,cli,log}=,
  =config.{RepoConfig,load_repo_config,discover_forge_root}=, the CMake, Rust,
  Gradle and Zig adapter constructors, =cmake_run.CMakeRunTarget= and =run_spec.RunSpec=.
  Preserve project parser/validation hooks and engine description, validation,
  preflight, optional preparation and execution hooks. This inventory records
  the existing surface, without promoting other internals to public APIs.
- CLI verbs, profiles, selection order, exit codes, forwarded argv and the
  =ZETA_BUILD_DONE= record are covered by the Forge regression suite.
- Native staging uses =build/staging/<profile>/<target>/= and a schema-1
  =.zeta-build-complete.json=. Published ownership and pending journal records
  use schema 1 beneath =<prefix>/share/zeta_forge/native/=. Conan state stays
  under =build/conan-state/<target>/<profile>/= with schema-1 Forge receipts
  and the Conan 2 lock format. The published OpenSSL manifest and CMake
  =.zeta-run/<CMake-profile>/<target>/= metadata use schema 1. The Rust
  catalog and project descriptors use schema 2, the project registry uses
  schema 1, and locked dependency reports use schema 2.
- Forge discovery considers the explicit =ZETAX_ROOT= workspace first. The
  selected Forge root determines the canonical workspace, builder and CMake
  utility paths. Inherited install prefix, third-party root, version and C++
  standard settings override defaults. Nonempty source overrides beat the
  derived third-party path or project default. Engine-specific profile and
  artifact mappings remain owned by their adapters.
