#+STARTUP: indent
#+TITLE: Zeta Forge Rust 工程治理

* 目标

=zeta_forge= 是 ZetaX Rust 工具链、第三方 crate 版本和工程检查规则的唯一来源。
业务仓库拥有自己的 Rust 源码、workspace 成员、功能组合和 =Cargo.lock=，但不再独立选择
工具链或第三方直接依赖版本。

该模式保留 Cargo 的原生工作方式：Cargo 继续解析 crate 和维护 lockfile；forge 负责统一
约束、环境和执行入口。Conan 只管理 C/C++ package，不管理纯 Rust crate。

* 公共基线

不可变公共基线位于 =rust/baselines/<rust-version>-r<revision>.toml=。文件名、内部 ID、
Rust 精确版本和修订号必须一致；forge 不提供隐式 current baseline 或旧 ID 回退。每个基线包含：

- Rust channel、profile、rustfmt 和 Clippy component；
- 第三方直接依赖的版本、来源、Git revision 和基础 feature；
- 按能力划分的依赖组。
- Cargo 安装工具的可执行文件与版本；当前 Dioxus CLI 固定为 0.7.10。

业务项目通过仓库根目录 =zeta-rust.toml= 精确选择基线和依赖组。例如：

#+begin_src toml
schema = 1
baseline = "1.97.1-r1"
manifest = "rust/Cargo.toml"
toolchain = "rust/rust-toolchain.toml"
default-profile = "release"
dependency-groups = ["foundation", "async-runtime", "native-nng", "dioxus-desktop"]
native-dependencies = ["nng", "openssl-conan"]
#+end_src

项目 workspace 必须在 =[workspace.metadata.zeta-forge]= 中记录同一基线。所有成员 crate
通过 =workspace = true= 使用第三方直接依赖；业务仓库内的 crate 之间使用 =path= 依赖。
workspace 必须提交一个 =Cargo.lock=。

Cargo 安装工具按 baseline 隔离在
=${ZETA_INSTALL_PREFIX}/share/zeta_forge/rust/<baseline-id>/bin=，不会回退到全局 =PATH=。
当前基线的 Dioxus CLI 安装命令为：

#+begin_src bash
cargo +1.97.1 install dioxus-cli --version 0.7.10 --locked \
  --root "${ZETA_INSTALL_PREFIX:-$HOME/.local}/share/zeta_forge/rust/1.97.1-r1"
#+end_src

* 命令

从 forge 根目录检查外部项目：

#+begin_src bash
./zbuild.py rust doctor --project-root ../zeta_trader
./zbuild.py rust metadata --project-root ../zeta_trader
./zbuild.py rust check --project-root ../zeta_trader --profile release
./zbuild.py rust build --project-root ../zeta_trader --profile release
./zbuild.py rust rebuild --project-root ../zeta_trader --profile release
./zbuild.py rust test --project-root ../zeta_trader --profile release
#+end_src

=doctor= 检查工程配置、精确 Rust toolchain/component 与原生依赖环境；=metadata= 使用 =--locked --offline= 验证已解析
依赖图；=check= 依次执行 rustfmt、Cargo check 和 Clippy；=build= 生成 workspace
产物；=rebuild= 只清理指定 profile 的 workspace member 后重新 build；=test= 运行整个
workspace 测试。所有编译命令接受 =--profile NAME=，省略时使用项目
=zeta-rust.toml= 中的 =default-profile=。
所有 Cargo 命令通过基线指定的 rustup toolchain 执行，不依赖用户全局默认版本。

Web/Fullstack 项目选择 =dioxus-web-fullstack= 依赖组，并在自己的 application feature
中组合 =dioxus/web=、=dioxus/server=、=dioxus/fullstack= 和 =dioxus/router=。
=rust doctor= 会按依赖组检查 Dioxus CLI 和 Web target，避免工具链基础检查通过但应用
仍无法构建或启动。

项目自己的 =zbuild.py= 可以复用 =zeta_forge.rust_workspace.RustWorkspaceManager=，组合
业务所需的资源生成、运行参数和验收流程。公共模块不感知业务 crate 或应用名称。

* 原生依赖

Rust binding 复用 forge 管理的原生库。当前 =nng= profile 要求安装前缀中存在 NNG header
和静态库，并向 Cargo child process 设置 =NNG_NO_VENDOR=1=、=NNG_DIR= 和 =NNG_STATIC=1=。
缺失时给出 forge 的安装命令，不自动安装、不回退到 Cargo vendored build。

=openssl-conan= profile 从 =./zbuild.py deps --BUILD_TYPE=Release --install= 生成的清单读取
Conan OpenSSL 版本及包目录；Rust 的 =dev= 和 =release= 均使用这套 Release 静态库。
构建器为 Cargo 设置同源的 =OPENSSL_DIR=、=OPENSSL_LIB_DIR=、=OPENSSL_INCLUDE_DIR=、
=OPENSSL_STATIC=1= 和 =OPENSSL_NO_VENDOR=1=，拒绝冲突的环境覆盖。gRPC 的 BoringSSL 安装不受影响。

* 升级规则

升级工具链或受管 crate 时，新增一个 =<rust-version>-r<revision>= 基线并验证公共测试，
不原地修改已经发布的基线。同一 Rust 版本的依赖修订递增 =rN=；Rust 版本变化时从 =r1=
开始。随后在业务仓库中同步 =zeta-rust.toml=、workspace metadata、=Cargo.toml=、
=rust-toolchain.toml= 和 =Cargo.lock=。未迁移的项目继续选择其原基线；不存在的旧 ID 会在
检查阶段明确失败。日常 check/test 不修改项目文件或 lockfile。
