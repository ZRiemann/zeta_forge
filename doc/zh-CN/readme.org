* Zeta Forge - 中文文档

[[file:../../readme.org][返回项目主页]] | [[file:../en/readme.org][English Version]]

Zeta Forge 是 ZetaX 的工程治理层，面向 C++ 与 Rust 项目统一管理源码、可复现构建、依赖版本和公共工程工具。

* 项目用途

Zeta Forge 有三个明确用途：

1. 提供公共工程工具：为 native 项目提供 Conan/CMake/Ninja 编排，为 Rust 项目提供 Cargo workspace 治理。
2. 协调 ZetaX 各项目版本，包括 submodule revision、C++ package、Rust toolchain、受管 crate 声明和共享构建默认值。
3. 为外部仓库提供可复用的项目管理 API。业务仓库只保留自身编排，并通过 =$ZETAX_ROOT/zeta_forge= 或附近兄弟目录复用公共能力。

* 克隆与初始化

建议在克隆时直接拉取全部 submodules：

#+begin_src bash
git clone --recurse-submodules <repo-url>
#+end_src

如果仓库已经克隆完成，可以再执行一次递归初始化：

#+begin_src bash
git submodule update --init --recursive
#+end_src

之所以要使用递归方式，是因为某些源码仓库自身也带有 submodules，例如 gRPC。

* Debian 系系统准备

在私有 ZetaX 环境中，环境准备可以拆成两层：

1. =zsa= 负责 Debian/Ubuntu 宿主机环境 bootstrap。
2. =zeta_forge= 负责仓库内部工具链和依赖准备。

如果 =zsa= 与 =zeta_forge= 以兄弟目录方式检出，可以先执行：

#+begin_src bash
../zsa/util/bootstrap_debian.sh --minimal
#+end_src

公共用户也可以手动准备同样的宿主机依赖，然后再执行 =zeta_forge= 仓库内准备脚本：

#+begin_src bash
./common/prepare_debian.sh
#+end_src

=./common/prepare_debian.sh= 专注于 =zeta_forge= 内部工具链管理：构建依赖、Conan 2 和 submodule 初始化。默认跟随 =zsa= 准备好的 ZetaX/uv Python 环境；只有项目确实需要固定 Conan Python runtime 时，才传入 =--python-version X.Y=。=zsa= 对公共用户不是必需前置条件。如果当前系统还没有 Python，这个 wrapper 会提示需要先安装的最小宿主机依赖；当存在兄弟目录 =zsa= 时，也会提示可选的 =../zsa/util/bootstrap_debian.sh --minimal= 辅助入口。

* 顶层统一构建入口

你可以直接在仓库根目录使用统一调度入口来触发构建：

#+begin_src bash
./zbuild.py build grpc hpx
./zbuild.py install grpc
./zbuild.py install hpx
./zbuild.py rebuild
../zeta_trader/zbuild.py doctor zeta_owl
#+end_src

=zbuild.py= 中的 =z= 取自 =zeta_forge=，用于表达仓库顶层统一入口，而不是局限于 CMake 的 =c=。
=zbuild.py= 可以直接执行，并分发到 =builder/= 下对应项目的工作区目标入口。
默认按 =deps grpc hpx folly nng= 顺序构建。build 仅使用项目内 staging；install 只发布显式指定且同 profile 已成功构建的库，不会重复构建或调用 Conan。
契约见 [[file:build.org][统一构建入口]]。上游测试尚未接入，Forge test 执行工具自身的 Python 测试。

* 源码布局

第三方源码目录位于 =3rd/= 下：

- =3rd/hpx=
- =3rd/folly=
- =3rd/grpc=
- =3rd/nng=
- =3rd/taskflow=
- =3rd/rapidjson=

外部 ZetaX 项目，例如 =zpp=，位于 =ZETAX_ROOT= 下与 =zeta_forge= 平级的位置，并把本仓库作为可复用工具链框架调用。
本仓库中的工作区目标入口默认都使用托管的 =3rd/*= submodules 作为源码输入。
工作区编排入口统一放在 =builder/= 目录下。
公共 CMake helper 模块位于 =cmake_util/=。该目录是遗留独立 =cmake_util= 项目的 ZetaX 维护副本，后续更新在 =zeta_forge= 内进行。
Rust 治理配置位于 =rust/=，公共实现位于 =common/zeta_forge/rust_workspace.py=。外部 Rust 项目保留源码和 lockfile，通过 =zeta-rust.toml= 使用 Forge 批准的依赖目录。

* Rust 项目管理

=rust/toolchains/= 管理精确 Rust 工具链；=rust/catalog.toml= 批准可并存的 crate 精确版本、
Git revision、Cargo 工具和应用能力。业务仓库通过 schema 2 的 =zeta-rust.toml= 声明
workspace、toolchain 文件、能力和原生库需求，通过 =[workspace.dependencies]= 选择
已批准版本，=Cargo.lock= 保留解析后的依赖图。项目拥有普通 Cargo feature 组合，
但必须遵守 bundled SQLite、原生 NNG binding 禁用默认 feature 等明确目录约束。
release/debug 默认值由公共 CLI 管理。

Dioxus CLI 等 Cargo 工具隔离安装到
=${ZETA_INSTALL_PREFIX}/share/zeta_forge/rust-tools/<channel>/<tool>/<version>=。
项目命令忽略全局 =PATH= 上的同名程序。=doctor= 只读检查隔离工具。
所选 Rust 交付物需要的工具缺失或版本不符时，=check=、=build=、=rebuild=、
=test=、=dev= 和 =fetch= 使用固定工具链与 =--locked= 安装批准版本。
工具准备在全部预检后、构建及 rebuild 清理前执行；安装需要访问 registry，
失败时不会清理项目构建状态。等价的独立安装命令是：

#+begin_src bash
cargo +1.97.1 install dioxus-cli --version 0.7.10 --locked --force \
  --root "${ZETA_INSTALL_PREFIX:-$HOME/.local}/share/zeta_forge/rust-tools/1.97.1/dioxus-cli/0.7.10"
#+end_src

#+begin_src bash
../zeta_trader/zbuild.py doctor zeta_owl
../zeta_trader/zbuild.py metadata zeta_owl
../zeta_trader/zbuild.py check zeta_owl --profile release
../zeta_trader/zbuild.py build zeta_owl --profile release
../zeta_trader/zbuild.py rebuild zeta_owl --profile release
../zeta_trader/zbuild.py test zeta_owl --profile release
#+end_src

=check= 执行 format、Cargo check 与 Clippy gate，不生成最终应用产物；=build= 生成
workspace 产物；=rebuild= 只清理指定 profile 的 workspace member 后重新构建，不清除 Cargo
下载源码缓存。公共 CLI 默认 release，debug 映射到 Cargo dev。

业务仓库拥有 workspace 成员、应用 feature、源码和 =Cargo.lock=。成员 crate 必须从 workspace 继承第三方依赖；所有非本地直接依赖必须匹配 Forge 目录。Cargo 继续负责 Rust package 解析，Conan 继续负责 native C/C++ package；NNG 等原生库由 forge 安装并传递给 Rust binding，禁止重复 vendored build。

=dioxus-web-fullstack= 能力检查已批准的 Dioxus、CLI 和 Web target。
业务项目仍然拥有 =dioxus/web=、=dioxus/server=、=dioxus/fullstack= 和
=dioxus/router= 等平台 feature 组合；这些 feature 不形成另一套依赖版本。
Web 目标如需去掉 release DWARF 调试符号，在项目构建定义中设置
=RustTarget(..., web_release_debug_symbols=False)=。
Forge 向 Dioxus release build 传入 =--debug-symbols false=；其他目标和 debug profile
保留 Dioxus 默认行为。项目 =doctor= 检查固定版本的 Dioxus CLI；Web 项目还检查
所选工具链的 =wasm32-unknown-unknown= target。SQLite 项目直接选择批准的
=rusqlite= 版本并启用所需的 =bundled= feature。

* ZetaX 工作区根目录

=ZETAX_ROOT= 是唯一公开的顶层工作区变量，例如 =~/git=。
标准布局中，=zeta_forge= 位于 =$ZETAX_ROOT/zeta_forge=，=zpp= 等外部项目位于 =$ZETAX_ROOT/zpp=。
=zsa= 可以在私有工作流中自动导出 =ZETAX_ROOT=，公共用户也可以手动设置。

项目入口需要复用共享编译工具库时，按以下顺序定位 =zeta_forge=：

1. 设置了 =ZETAX_ROOT= 时，使用 =$ZETAX_ROOT/zeta_forge=。
2. 使用兄弟目录中的 =zeta_forge= checkout。

* 覆盖源码目录

如果你希望使用自己的本地源码仓库，而不是 zeta_forge 管理的 submodules，可以在运行工作区目标入口前覆盖对应环境变量：

#+begin_src bash
export ZETA_GRPC_SRC_DIR=/path/to/grpc
export ZETA_HPX_SRC_DIR=/path/to/hpx
export ZETA_FOLLY_SRC_DIR=/path/to/folly
export ZETA_NNG_SRC_DIR=/path/to/nng
export ZETA_TASKFLOW_SRC_DIR=/path/to/taskflow
export ZETA_RAPIDJSON_SRC_DIR=/path/to/rapidjson
export ZETAX_ROOT=/path/to/zetax-workspace
export ZETA_3RD_DIR=/path/to/zeta_forge/3rd
export ZETA_INSTALL_PREFIX=/path/to/install/prefix
#+end_src

如果没有显式覆盖，第三方源码路径默认使用 =3rd/= 下对应的 submodule 路径。

=ZETA_INSTALL_PREFIX= 默认值为 =~/.local=。

* 工作区目标入口示例

#+begin_src bash
./zbuild.py build deps --profile debug
./zbuild.py install deps --profile debug
./zbuild.py build grpc hpx folly nng
./zbuild.py install grpc
./zbuild.py install hpx
./zbuild.py install folly
./zbuild.py install nng
#+end_src

=deps= 是 =zpp=、=zeta_trader= 等外部项目消费公共 C++ package config 的统一 Conan 入口。
显式 =install deps= 将 Conan package 文件发布到
=${ZETA_INSTALL_PREFIX}/lib/cmake/zeta_deps/<BUILD_TYPE>=。外部项目应消费该安装环境，
不要为 =spdlog=、=fmt=、=GTest=、=SQLite3= 等共享依赖重复维护自己的 Conan 依赖图。

* 外部 zpp 入口

=zpp= 是位于 =$ZETAX_ROOT/zpp= 的独立 ZetaX 项目。它只维护项目级构建逻辑，共享 Conan 依赖版本和 package config 由 =zeta_forge deps= 统一提供。

#+begin_src bash
cd "$ZETAX_ROOT/zeta_forge"
./zbuild.py build deps --profile debug
./zbuild.py install deps --profile debug
cd "$ZETAX_ROOT/zpp"
./zbuild.py rebuild --profile debug
#+end_src

该入口默认把当前 =zpp= checkout 作为 =ZETA_ZPP_SRC_DIR=，除非用户显式设置了这个变量。
它会通过 =$ZETAX_ROOT/zeta_forge= 或附近兄弟目录复用共享编译工具库，zpp 特有构建逻辑位于 =zpp/builder/=。
它也会通过 =$ZETAX_ROOT/zeta_forge/cmake_util= 复用公共 CMake helper 模块，不再携带 =cmake_util= submodule。
共享依赖的 Conan 解析只在 =zeta_forge deps= 中执行，其中包括 =spdlog=、=fmt= 和 =SQLite3= 等公共依赖版本。

* 当前说明

- gRPC 是工作区内核心 RPC 依赖族的统一来源：Abseil、Protobuf、zlib、TLS/BoringSSL、c-ares、RE2、upb、utf8_range、xxhash 和 address_sorting。
- HPX 默认关闭 examples、tests 及性能测试目标；保留 =hpxdep=、=inspect= 工具，并继续安装 =hpx_stat_viewer.py=。
- HPX 通过 =HPX_WITH_FETCH_STDEXEC=ON= 固定获取 commit =04de75de5807e73a229acf047c6976575e313359= 的 stdexec，使安装后的 execution API 与托管的 =3rd/hpx= 源码修订保持一致。
- gRPC 的测试/工具生态依赖，例如 benchmark、bloaty、googletest、googleapis、xDS、Envoy API、protoc-gen-validate 和 OpenTelemetry C++，默认不作为 Zeta Forge 开发依赖安装。
- 外部 zpp 构建默认使用 =3rd/taskflow= 和 =3rd/rapidjson=。
- RapidJSON 通过 =RAPIDJSON_ROOT= 传递给 zpp。
- zpp 可选 HPX 模块会同时消费已安装 HPX 与 forge 的 Asio/Hwloc 兼容配置，并拒绝 =HPX_GIT_COMMIT= 与当前 =3rd/hpx= 源码不一致的安装。
