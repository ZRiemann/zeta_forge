* Zeta Forge

Zeta Forge is a superproject for unified source management, reproducible builds, and dependency integration across modern C++ libraries and applications.

中文 README: [[file:doc/readme_cn.org][doc/readme_cn.org]]

* Project Purpose

Zeta Forge has three explicit roles:

1. It is the shared build toolchain framework for managed =3rd/*= source projects and external ZetaX projects such as =zpp=, including Conan/CMake/Ninja orchestration, source directory resolution, install prefix management, reusable project build primitives, and shared CMake helper modules.
2. It coordinates versions across the workspace, including submodule revisions, third-party dependency versions, shared build defaults, and project-specific build recipes.
3. It is a reusable toolchain framework for external systems. A project outside this repository can locate =zeta_forge= through =$ZETAX_ROOT/zeta_forge= or a nearby sibling checkout, reuse the common build library, and avoid maintaining a parallel dependency/toolchain stack.

* Clone And Initialize

Clone with submodules:

#+begin_src bash
git clone --recurse-submodules <repo-url>
#+end_src

If the repository has already been cloned, initialize all submodules recursively:

#+begin_src bash
git submodule update --init --recursive
#+end_src

This is required because some source repositories also contain nested submodules, for example gRPC.

* Prepare Debian-Based Systems

For private ZetaX environments, the preparation flow can be split into two layers:

1. =zsa= bootstraps the Debian/Ubuntu host environment.
2. =zeta_forge= prepares repo-local toolchains and dependencies.

If =zsa= is checked out next to =zeta_forge=, you can bootstrap the host with:

#+begin_src bash
../zsa/util/bootstrap_debian.sh --minimal
#+end_src

Public users can prepare the same host packages manually, then prepare the =zeta_forge= workspace with:

#+begin_src bash
./common/prepare_debian.sh
#+end_src

=./common/prepare_debian.sh= focuses on =zeta_forge=-local toolchain management: build dependencies, Conan 2, and submodule initialization. By default it follows the active ZetaX/uv Python environment prepared by =zsa=; pass =--python-version X.Y= only when a project needs an explicit Conan Python runtime. =zsa= is optional for public users. If Python is not available yet, the wrapper prints the minimal host packages that must be installed first; when a sibling =zsa= checkout exists, it also shows the optional =../zsa/util/bootstrap_debian.sh --minimal= helper.

* Unified Build Entry

You can invoke builds from the repository root through the unified dispatcher:

#+begin_src bash
./zbuild.py grpc --rebuild --install
./zbuild.py hpx --rebuild --install
./zbuild.py all --rebuild
#+end_src

=zbuild.py= uses the =z= from =zeta_forge= to represent the top-level workspace entry rather than a CMake-specific command.
=zbuild.py= can be executed directly and routes commands to the corresponding workspace target entrypoints under =builder/=.
When running =./zbuild.py all=, the dispatcher builds =grpc= first, treats =hpx= and =nng= as independent targets, then builds =folly= after =grpc=.
The managed third-party entrypoints disable upstream examples and tests by default so that =all= and individual target builds focus on installable libraries. gRPC code-generation plugins remain enabled, HPX builds its =hpxdep= and =inspect= tools, and Folly retains its upstream-installed =libfolly_test_util.a= support library.

* Source Layout

Third-party source checkouts live under =3rd/=:

- =3rd/hpx=
- =3rd/folly=
- =3rd/grpc=
- =3rd/nng=
- =3rd/taskflow=
- =3rd/rapidjson=

External ZetaX projects such as =zpp= live next to =zeta_forge= under =ZETAX_ROOT= and call this repository as a reusable toolchain framework.
The workspace target entrypoints in this repository use the managed =3rd/*= submodules by default.
The workspace orchestration entrypoints live under =builder/=.
Shared CMake helper modules live under =cmake_util/=. This directory is the maintained ZetaX copy of the legacy standalone =cmake_util= project.

* ZetaX Workspace Root

=ZETAX_ROOT= is the only public top-level workspace variable, for example =~/git=.
With the standard layout, =zeta_forge= lives at =$ZETAX_ROOT/zeta_forge= and external projects such as =zpp= live at =$ZETAX_ROOT/zpp=.
=zsa= can export =ZETAX_ROOT= for private workflows, but public users may set it manually.

When a project entrypoint needs the shared build library, it resolves =zeta_forge= in this order:

1. =$ZETAX_ROOT/zeta_forge= when =ZETAX_ROOT= is set.
2. nearby =zeta_forge= directories discovered from the entrypoint path.

* Override Source Directories

If you want to build against your own local checkout instead of the managed submodules, override the corresponding environment variable before running a workspace target entrypoint:

#+begin_src bash
export ZETA_GRPC_SRC_DIR=/path/to/grpc
export ZETA_HPX_SRC_DIR=/path/to/hpx
export ZETA_FOLLY_SRC_DIR=/path/to/folly
export ZETA_NNG_SRC_DIR=/path/to/nng
export ZETA_TASKFLOW_SRC_DIR=/path/to/taskflow
export ZETA_RAPIDJSON_SRC_DIR=/path/to/rapidjson
export ZETAX_ROOT=/path/to/zetax-workspace
export ZETA_3RD_DIR=/path/to/zeta_forge/3rd
export ZETA_INSTALL_PREFIX=/path/to/install/prefix
#+end_src

If an override is not provided, third-party source paths default to the corresponding path under =3rd/=.

By default, =ZETA_INSTALL_PREFIX= is set to =~/.local=.

* Workspace Target Entrypoints

Examples:

#+begin_src bash
./zbuild.py conan --BUILD_TYPE=Debug --install
./builder/deps/zbuild.py --BUILD_TYPE=Debug --install
./builder/grpc/zbuild.py --rebuild --install
./builder/hpx/zbuild.py --rebuild --install
./builder/folly/zbuild.py --rebuild --install
./builder/nng/zbuild.py --rebuild --install
#+end_src

=deps= is the single ZetaX Conan entrypoint for common C++ package configs
consumed by external projects such as =zpp= and =zeta_trader=. The top-level
=conan= command is an alias for =deps= when only the Conan-managed dependency
environment is needed. It installs
Conan-generated package files under
=${ZETA_INSTALL_PREFIX}/lib/cmake/zeta_deps/<BUILD_TYPE>=. External projects
should consume that installed environment and should not run their own Conan
dependency graph for shared packages such as =spdlog=, =fmt=, =GTest=, or =SQLite3=.

* External zpp Entrypoint

=zpp= is an independent ZetaX project under =$ZETAX_ROOT/zpp=. It owns only project-specific build logic, while shared Conan dependency versions and package configs are owned by =zeta_forge deps=.

#+begin_src bash
cd "$ZETAX_ROOT/zeta_forge"
./zbuild.py conan --BUILD_TYPE=Debug --install
cd "$ZETAX_ROOT/zpp"
./zbuild.py --rebuild --no-tests
#+end_src

The entrypoint uses the current =zpp= checkout as =ZETA_ZPP_SRC_DIR= unless that variable is explicitly set.
It reuses the shared build library from =$ZETAX_ROOT/zeta_forge= or a nearby sibling checkout, while zpp-specific build logic lives under =zpp/builder/=.
It also consumes shared CMake helper modules from =$ZETAX_ROOT/zeta_forge/cmake_util= instead of carrying a =cmake_util= submodule.
The shared Conan dependency versions, including =spdlog=, =fmt=, and =SQLite3=, are owned by =zeta_forge deps=.

* Current Notes

- gRPC is the workspace source for the core RPC dependency family: Abseil, Protobuf, zlib, TLS/BoringSSL, c-ares, RE2, upb, utf8_range, xxhash, and address_sorting.
- HPX examples and tests, including performance-test targets, are disabled by default; the =hpxdep= and =inspect= tools remain enabled and =hpx_stat_viewer.py= remains installable.
- HPX always fetches stdexec at commit =05e3f5ec59655fee2536fc3116e5ffb4927ae955= through =HPX_WITH_FETCH_STDEXEC=ON=; this keeps the installed execution API aligned with the managed =3rd/hpx= source revision.
- gRPC test/tooling ecosystem dependencies such as benchmark, bloaty, googletest, googleapis, xDS, Envoy API, protoc-gen-validate, and OpenTelemetry C++ are not installed as default Zeta Forge development dependencies.
- External zpp builds use Taskflow and RapidJSON from =3rd/= by default.
- RapidJSON is passed to zpp through =RAPIDJSON_ROOT=.
- zpp's optional HPX module consumes the installed HPX package together with the forge Asio/Hwloc compatibility configs and rejects an installation whose =HPX_GIT_COMMIT= differs from the current =3rd/hpx= source.
